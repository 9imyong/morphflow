# 장애 시나리오 Runbook (A/B/C 전환 연계)

## 1. 문서 목적
이 문서는 주요 장애 시나리오별로 다음 항목을 표준화해 운영 대응 속도를 높이기 위한 Runbook이다.

1. 예측/탐지 지표
2. 1차 대응(즉시 조치)
3. 복구 절차
4. 후속 RCA/재발방지
5. A/B/C 아키텍처 전환 판단 연결

---

## 2. 공통 운영 원칙
- 우선순위: 사용자 영향 최소화 -> 데이터 정합성 보존 -> 원인 분석
- 장애 조치 중 변경사항(스케일, 설정, 재시작)은 반드시 시간순 로그로 기록
- 임시 완화 조치와 영구 해결 조치를 분리해 관리

---

## 3. 시나리오별 대응

### 3.1 Kafka lag 급증

증상/예측 지표:
- `max(kafka_consumergroup_lag)` 임계치 지속 초과
- `WorkerProcessingTimeHigh` 경고 동반 발생
- request-topic 적체 증가

1차 대응:
1. `kafka-exporter`/consumer target 상태(`up`) 확인
2. worker pod/container 인스턴스 수를 우선 수평 확장
3. 장애 worker 인스턴스(메모리 누수/에러 반복) 분리 재기동

복구 절차:
1. lag 감소 추세 확인(임계치 미만 복귀)
2. 처리율(consume/s)과 실패율을 동시에 확인
3. 확장 이전 수준으로 되돌릴 때는 단계적 축소

후속 조치:
- 반복 발생 시 B 전환 검토(추론 전용 worker 분리)
- lag 급증 시간대의 입력량 패턴/배치성 요청 분석

A/B/C 전환 판단:
- **A -> B 우선 검토** (처리 병목이 worker 내부 추론 구간에 집중될 때)

---

### 3.2 Worker 처리 지연

증상/예측 지표:
- `histogram_quantile(0.95, sum(rate(worker_job_processing_seconds_bucket[5m])) by (le))` 상승
- SUCCESS 전환 시간 증가
- 처리 timeout/재시도 비율 증가

1차 대응:
1. 최근 배포/설정 변경 여부 즉시 확인(롤백 기준 판단)
2. worker 리소스(CPU/메모리) 사용률 점검
3. 임계 구간에서 동시 처리량 제한 또는 임시 scale-out 적용

복구 절차:
1. p95 처리시간 기준치 회복 여부 확인
2. FAILED 건 재처리 정책 적용(중복 방지 키 확인)
3. backlog 정상화 후 임시 제한 해제

후속 조치:
- 처리 단계별 세부 타이밍 계측 강화(전처리/추론/저장 분리)
- 장기적으로 inference/downstream 분리 로드맵 반영

A/B/C 전환 판단:
- 추론 비중 지연이면 **A -> B**
- 저장/외부연동 비중 지연이면 **A -> C**

---

### 3.3 DB latency 증가

증상/예측 지표:
- `PostgresResponseSlow` 경고
- 쿼리 응답 지연 및 API p95 증가
- 커넥션 대기 시간/락 대기 증가

1차 대응:
1. 느린 쿼리 및 락 대기 세션 우선 확인
2. 불필요한 대량 배치성 요청/관리 작업 일시 중지
3. DB 리소스 한계(CPU/IO/디스크) 점검

복구 절차:
1. 병목 쿼리 튜닝(인덱스/실행계획 확인)
2. 문제 트랜잭션 정리 후 정상 트래픽 복귀 확인
3. 필요 시 읽기/쓰기 부하 분산 전략 적용

후속 조치:
- 상위 N개 느린 쿼리 상시 추적
- 스키마/인덱스 변경은 migration + 성능 검증 절차에 편입

A/B/C 전환 판단:
- 후단 저장/연동 단계 병목이 지속되면 **A -> C**

---

### 3.4 Redis 장애

증상/예측 지표:
- Redis exporter down 또는 ping 실패
- 멱등성 키 조회/저장 실패
- 중복 요청 방어 불안정(동일 요청 재처리 위험)

1차 대응:
1. Redis 프로세스/네트워크 단절 여부 확인
2. Redis 재시작 또는 대체 노드 전환(가능 시)
3. 장애 시간대 중복 처리 위험 구간 식별 및 임시 보호 조치

복구 절차:
1. Redis 연결 복구 후 API/worker 정상 동작 확인
2. 장애 시간대 요청 중 중복 처리 후보 검증
3. 필요 시 DB unique 제약 기반 정합성 재검증

후속 조치:
- Redis HA(센티널/클러스터) 검토
- 멱등성 실패 시 fallback 전략(DB 검사 강화) 정의

A/B/C 전환 판단:
- Redis 자체는 A/B/C 전환 트리거보다는 기반 안정성 이슈로 분류
- 다만 반복 시 전체 아키텍처 확장보다 인프라 안정화가 우선

---

### 3.5 Retry / DLQ 급증

증상/예측 지표:
- `increase(dlq_messages_total[5m]) > 0` 지속 발생
- `increase(retry_published_total[5m]) / increase(retry_failure_total[5m])` 비율 악화
- 동일 `error-reason` 헤더가 반복되는 DLQ 적재

1차 대응:
1. 최근 배포/설정 변경과 외부 의존성 장애를 우선 확인
2. DLQ 메시지의 `original-topic`, `retry-count`, `error-reason` 헤더로 실패 유형 분류
3. 고정 오류(스키마 불일치/필수 필드 누락)는 즉시 재처리 중지 후 원인 수정

복구 절차:
1. 원인 수정 후 샘플 메시지 1건 replay로 정상 처리 확인
2. 배치 replay 전 `retry_max_count`, backoff 설정 적정성 점검
3. replay 이후 lag, 실패율, DLQ 증가율 안정화 확인

후속 조치:
- 오류 유형별 DLQ 분류 정책(스키마/의존성/타임아웃) 추가
- 반복 오류는 producer validation 또는 스키마 레지스트리 도입 검토

A/B/C 전환 판단:
- GPU 추론 구간 오류/지연이 주원인이면 **A -> B**
- 다운스트림 저장/연동 실패가 주원인이면 **A -> C**

---

## 4. RCA/재발방지 표준 절차

1. 사고 타임라인 정리
- 탐지 시각, 고객 영향 시작/종료, 완화/복구 시각을 분 단위로 기록

2. 원인 분류
- 직접 원인(Immediate Cause)
- 시스템 원인(Systemic Cause)
- 감지 실패/대응 지연 요인

3. 재발방지 액션
- 코드/설정/인프라/운영 절차로 분리
- 각 액션에 담당자, 기한, 검증 기준 부여

4. 검증
- 동일 시나리오 리허설(게임데이 또는 부하테스트)
- 알람 민감도/오탐률 재점검

5. 문서 반영
- 본 Runbook, 아키텍처 문서, 작업 로그를 동시에 업데이트

---

## 5. 즉시 실행 체크리스트

1. 영향 범위 파악(요청 실패율, 지연, backlog)
2. 관련 알람/대시보드 확인(Prometheus/Grafana/Kibana)
3. 시나리오별 1차 대응 실행
4. 복구 확인 후 RCA 이슈 생성
5. A/B/C 전환 필요성 평가 및 의사결정 기록
