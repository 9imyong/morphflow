# ADR-0002: Redis 예약과 데이터베이스 상태 확인을 결합한 멱등성 보장

## 맥락

at-least-once 전달을 전제하므로 중복이 반드시 발생합니다. 클라이언트 재시도, 프로듀서 재전송, 오프셋 커밋 전 장애, 재시도 토픽 재유입이 모두 중복 경로입니다. 중복 처리는 결과 중복 반영과 불필요한 자원 소모로 이어집니다.

## 결정 기준

- 정상 경로에서 빠를 것
- 저장소 장애 시 중복 완료로 이어지지 않을 것
- 영구 잠금이 발생하지 않을 것
- 실패한 작업이 다시 시도될 수 있을 것

## 검토한 대안

### 대안 1: 데이터베이스 유니크 제약만 사용

- 장점: 단일 기준. 추가 구성 요소 없음
- 단점: 중복 요청마다 데이터베이스 쓰기 시도와 예외 처리가 발생
- 위험: 동시 처리 중복은 막지 못하고 결과 중복 기록만 막음

### 대안 2: Redis 잠금만 사용

- 장점: 빠르고 동시 처리 차단에 적합
- 단점: Redis가 비거나 TTL이 만료되면 보호가 사라짐
- 위험: Redis를 신뢰 기준으로 삼으면 장애 시 중복 완료 발생

### 대안 3: Redis 예약을 1차, 데이터베이스 상태를 2차 기준으로 결합

- 장점: 정상 경로는 Redis로 빠르게 차단하고, 최종 판단은 기준 저장소에서 수행
- 단점: 두 저장소의 상태를 함께 다루어야 함
- 위험: 두 단계의 의미를 혼동하면 잘못된 스킵이 발생

## 결정

대안 3을 채택합니다.

- 요청 단계: `idem:req:{Idempotency-Key}`를 `SET NX EX`로 예약합니다. 이미 존재하면 기존 `job_id`를 반환합니다.
- 처리 단계: `idem:job:{job_id}`를 `SET NX EX`로 예약합니다.
- **예약에 실패하면 데이터베이스의 현재 상태를 확인합니다.** 이미 `SUCCESS`인 경우에만 안전하게 커밋하고, 그 외에는 재시도 경로로 보냅니다.
- **처리 실패 시 잠금을 삭제합니다.** 성공한 경우에만 `COMPLETED` 상태로 잠금을 유지합니다.
- 모든 키에 TTL을 부여해 영구 잠금을 방지합니다.

## 결과

### 긍정적 결과

- Redis가 비어 있어도 데이터베이스 상태 확인이 중복 완료를 막습니다.
- 실패한 작업은 잠금이 해제되어 재시도가 즉시 가능합니다.
- 잠금 경합 상황이 조용한 메시지 소실이 아니라 재시도 경로로 이어집니다.

### 부정적 결과와 비용

- 잠금 경합이 일반 처리 실패와 동일하게 재시도 횟수를 소모합니다. 장시간 처리 중인 Job의 중복 메시지가 DLQ로 갈 수 있습니다.
- `DownstreamPipelineService`는 아직 처리 잠금을 사용하지 않고 상태 확인만 수행합니다.
- TTL 만료 이후 재전달되면 전체 재처리가 발생합니다.

### 후속 작업

- [x] 잠금 경합을 성공 처리하지 않고 재시도 경로로 보내도록 수정
- [ ] 잠금 경합을 일반 실패와 분리해 재시도 횟수를 소모하지 않도록 개선
- [ ] downstream 경로에도 동일한 처리 잠금 적용

## 검증 방법

잠금 경합 회귀 테스트(`tests/test_lock_recovery_flow.py`)와 재시도 후 복구 테스트(`tests/test_retry_runtime.py`)로 확인합니다. 중복 완료가 발생하면 결정을 재검토합니다.
