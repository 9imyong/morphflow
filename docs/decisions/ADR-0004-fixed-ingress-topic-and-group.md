# ADR-0004: 아키텍처 모드 전환 시 진입 토픽과 컨슈머 그룹 고정

## 맥락

초기 설계에서는 모드마다 진입 토픽을 달리하는 방안을 검토했습니다(A는 `request-topic`, B·C는 `inference-topic`). 그러나 모드 전환은 **운영 중**에 일어납니다. 전환 시점에 진입 토픽이나 컨슈머 그룹이 바뀌면 이전 토픽에 남아 있던 메시지를 아무도 소비하지 않게 되고, 컨슈머 그룹이 바뀌면 오프셋이 초기화되어 이미 처리한 메시지를 다시 처리하거나 미처리 메시지를 건너뛰게 됩니다.

## 결정 기준

- 전환 중 메시지가 유실되거나 중복 처리되지 않을 것
- 전환이 특별한 데이터 이관 절차 없이 가능할 것
- lag 지표가 전환 전후로 연속성을 가질 것

## 검토한 대안

### 대안 1: 모드별로 진입 토픽 분리

- 장점: 모드별 흐름이 토픽 이름에 드러나 이해가 쉬움
- 단점: 전환 시 이전 토픽의 잔여 메시지 처리 절차가 별도로 필요
- 위험: 전환 순간 백로그 유실

### 대안 2: 진입 토픽과 컨슈머 그룹을 고정하고 역할만 교체

- 장점: 전환이 워커 교체만으로 완료되며 백로그와 오프셋이 연속됨
- 단점: 토픽 이름이 실제 역할을 설명하지 않음
- 위험: 설정에 남은 미사용 토픽이 혼란을 줄 수 있음

## 결정

대안 2를 채택합니다.

- API는 모드와 무관하게 항상 `KAFKA_REQUEST_TOPIC`으로 발행합니다.
- `unified`와 `inference` 역할은 같은 컨슈머 그룹 `architecture-main-worker`를 사용합니다.
- `downstream` 역할만 별도 그룹 `architecture-main-worker-downstream`을 사용합니다. 소비하는 토픽 자체가 다르기 때문입니다.
- 분리가 필요한 것은 추론 **이후** 단계이며, 이는 새 토픽(`downstream-topic`)을 추가하는 방식으로 해결합니다.

## 결과

### 긍정적 결과

- A ↔ B 전환이 워커 배포 교체만으로 완료됩니다. 백로그와 오프셋이 그대로 유지됩니다.
- `request-topic` lag 지표를 전환 전후로 동일하게 비교할 수 있습니다.

### 부정적 결과와 비용

- `inference-topic` 설정이 남아 있고 토픽도 자동 생성되지만 어떤 역할도 사용하지 않습니다. 정리가 필요합니다.
- 토픽 이름만으로는 어떤 역할이 소비하는지 알 수 없어 문서 의존도가 높아집니다.

### 후속 작업

- [ ] 미사용 `KAFKA_INFERENCE_TOPIC` 설정과 토픽 자동 생성 제거

## 검증 방법

모드를 전환한 뒤 컨슈머 그룹의 오프셋이 이어지는지 `scripts/kafka-consumer-group-describe.sh`로 확인합니다.
