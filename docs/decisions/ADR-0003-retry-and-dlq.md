# ADR-0003: 헤더 기반 재시도와 DLQ 격리

## 맥락

처리 실패에는 일시적 실패(의존성 순간 지연)와 영구적 실패(잘못된 payload)가 섞여 있습니다. 구분 없이 재시도하면 영구 실패가 파티션을 막고, 구분 없이 버리면 복구 가능한 작업을 잃습니다.

## 결정 기준

- 재시도가 소비를 무한히 막지 않을 것
- 실패 원인을 사후에 분류할 수 있을 것
- 원본 메시지를 보존해 재주입이 가능할 것
- 역할이 여러 개일 때 재시도가 섞이지 않을 것

## 검토한 대안

### 대안 1: 오프셋을 커밋하지 않고 같은 메시지를 반복 소비

- 장점: 구현이 없음
- 단점: 영구 실패 시 파티션이 영구 정지
- 위험: 단일 메시지가 전체 처리를 중단시킴

### 대안 2: 실패 시 즉시 DLQ

- 장점: 단순하고 파이프라인이 막히지 않음
- 단점: 일시적 실패까지 수동 개입 대상이 됨
- 위험: DLQ 신호가 과다해져 의미를 잃음

### 대안 3: 제한 횟수까지 재시도 토픽으로 순환 후 DLQ

- 장점: 일시적 실패는 자동 복구, 영구 실패는 격리
- 단점: 재시도 토픽과 헤더 관리가 필요
- 위험: 백오프 처리 위치에 따라 소비 지연 발생

## 결정

대안 3을 채택합니다.

- 재시도 메타데이터는 Kafka 헤더로 전달합니다: `retry-count`, `original-topic`, `error-reason`
- `RETRY_MAX_COUNT`까지 지수 백오프 후 재시도 토픽으로 재발행하고, 초과하면 `dlq-topic`으로 보냅니다.
- 재시도 토픽은 역할별로 분리합니다: 추론 경로는 `retry-topic`, 후단 경로는 `retry-downstream-topic`
- 워커는 자신의 소비 토픽과 `original-topic`이 다른 재시도 메시지를 건너뜁니다.
- **DLQ 메시지는 원본 payload를 그대로 보존**해 원인 수정 후 재주입할 수 있게 합니다.

## 결과

### 긍정적 결과

- 일시적 실패가 자동으로 복구되며, 재시도 후 성공 경로를 회귀 테스트로 검증했습니다.
- `error-reason` 헤더로 DLQ 적재 원인을 분류할 수 있습니다.
- `dlq_messages_total` 증가를 경보로 연결해 영구 실패를 즉시 감지합니다.

### 부정적 결과와 비용

- 백오프 대기를 소비 루프 안에서 수행하므로 대기 중에는 커밋과 폴링이 멈춥니다.
- 역할 핸들러가 값을 반환하지 않고 예외를 던지면 이 경로를 타지 않습니다. 해당 메시지는 재시도·DLQ 없이 재소비가 반복됩니다.
- 잠금 경합도 재시도 횟수를 소모합니다.
