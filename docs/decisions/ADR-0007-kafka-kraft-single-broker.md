# ADR-0007: Kafka KRaft 모드 단일 브로커와 토픽 자동 구성

## 맥락

로컬 검증 환경에서 ZooKeeper를 함께 운영하면 컨테이너 수와 기동 시간이 늘고, 기동 순서 문제도 추가됩니다. 또한 애플리케이션이 기대하는 토픽과 파티션 수가 브로커의 실제 상태와 어긋나면 컨슈머 확장이 조용히 무력화됩니다.

## 결정 기준

- 로컬 기동이 단순할 것
- 애플리케이션이 기대하는 토픽 구성이 보장될 것
- 파티션 수 변경이 반영될 것

## 검토한 대안

### 대안 1: ZooKeeper 기반 구성 유지

- 장점: 자료가 많고 익숙함
- 단점: 컨테이너와 기동 순서가 추가됨
- 위험: 이후 버전에서 제거 예정인 방식에 의존

### 대안 2: KRaft 단일 노드 + 자동 생성에 의존

- 장점: 구성이 가장 단순
- 단점: 자동 생성 토픽은 기본 파티션 수를 따르므로 의도한 파티션 수를 얻지 못함
- 위험: 컨슈머를 늘려도 파티션이 1이면 확장되지 않음

### 대안 3: KRaft 단일 노드 + 애플리케이션 기동 시 토픽 보정

- 장점: 애플리케이션이 기대하는 파티션 수를 보장. 기존 토픽도 확장
- 단점: 기동 시 관리 클라이언트 접근 권한 필요
- 위험: 운영 환경에서는 토픽 관리 주체가 달라질 수 있음

## 결정

대안 3을 채택합니다.

- Kafka는 KRaft 모드 단일 노드로 운영하고 replication factor는 1로 둡니다.
- API와 워커는 기동 시 `ensure_kafka_topics()`로 필요한 토픽을 생성하고, 목표 파티션 수보다 적으면 확장합니다.
- 파티션 수는 축소하지 않습니다. Kafka가 축소를 지원하지 않기 때문입니다.
- 이 동작은 `KAFKA_TOPIC_AUTO_CONFIGURE`로 끌 수 있습니다.

## 결과

### 긍정적 결과

- 브로커 구성이 단일 컨테이너로 단순해졌습니다.
- 애플리케이션과 브로커의 토픽 구성 불일치가 제거되었습니다.
- 파티션 수를 설정으로 올릴 수 있어 컨슈머 확장 실험이 가능합니다.

### 부정적 결과와 비용

- replication factor 1이므로 브로커 장애 시 데이터가 유실됩니다. 로컬 검증 환경의 의도된 제약입니다.
- 애플리케이션이 토픽 관리 권한을 가집니다. 운영 환경에서는 권한 분리가 필요합니다.

### 후속 작업

- [ ] 운영 환경 전환 시 토픽 관리 주체 분리와 replication factor 재설정

## 검증 방법

`scripts/kafka-topic-list.sh`로 토픽과 파티션 수를 확인하고, `tests/test_kafka_topics.py`·`tests/test_container_topics.py`로 목표 계산 로직을 검증합니다.
