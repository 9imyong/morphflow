# ADR-0001: 병목 위치에 따라 전환하는 단일 서비스 구조 채택

## 맥락

두 종류 이상의 아키텍처를 실제로 배포해 장애 대응 능력을 보여야 했습니다. 동시에 추론 파이프라인의 병목은 사전에 특정할 수 없었습니다. 추론 자체가 느릴 수도, 추론 이후의 저장·전달 단계가 느릴 수도 있으며 둘은 완전히 다른 대응을 요구합니다.

처음부터 최대로 분리된 구조를 만들면 운영 복잡도만 커지고, 단일 구조로 시작하면 병목이 생겼을 때 구조를 다시 설계해야 합니다.

## 결정 기준

- 병목 구간을 관측 데이터로 식별할 수 있는가
- 구조를 바꿀 때 API 계약과 누적된 데이터가 보존되는가
- 전환에 드는 운영 비용이 낮은가
- 두 개 이상의 구조를 실제로 배포해 비교할 수 있는가

## 검토한 대안

### 대안 1: 처음부터 완전히 분리된 파이프라인

- 장점: 각 단계를 독립적으로 확장 가능. 구조 변경이 필요 없음
- 단점: 초기 운영 복잡도가 높고, 분리가 불필요한 구간까지 토픽·워커·배포 단위가 늘어남
- 위험: 병목이 없는 구간을 분리해 지연만 추가할 수 있음

### 대안 2: 단일 구조로 구현하고 필요 시 재설계

- 장점: 가장 단순하고 빠름
- 단점: 전환 시 API·데이터·오프셋 연속성을 보장하기 어려움
- 위험: 사실상 두 번 만들게 됨

### 대안 3: 하나의 코드베이스에서 설정으로 역할을 전환

- 장점: 공통 계약을 유지한 채 병목 구간만 분리 가능. 같은 이미지로 여러 구조를 배포해 비교 가능
- 단점: 역할 조립 분기가 코드에 남고, 모드 조합만큼 검증 경로가 늘어남
- 위험: 모드별 동작 차이가 문서화되지 않으면 운영 혼선

## 결정

대안 3을 채택합니다. A(통합), B(추론 분리), C(후단 분리), BC(동시 적용)를 **같은 서비스의 운영 모드**로 정의하고, `ARCHITECTURE_MODE`와 `WORKER_ROLE` 환경 변수로 전환합니다.

전환과 무관하게 다음을 고정합니다.

- HTTP API 계약
- Job 상태 모델
- 이벤트 Envelope 형식
- 멱등성 키 전략
- 데이터베이스 스키마
- 지표 이름과 라벨

역할 조립은 `app/workers/roles.py`의 `build_worker_role()` 한 곳에서만 수행합니다.

## 결과

### 긍정적 결과

- 같은 이미지로 A·B·C를 배포해 동일 부하 조건에서 비교했습니다. 결과는 [품질](../architecture/quality.md)에 있습니다.
- 모드 전환이 Kustomize 오버레이의 설정 패치와 워커 추가만으로 이루어집니다.
- 지표 이름이 고정되어 전환 전후 비교가 가능합니다.

### 부정적 결과와 비용

- `build_worker_role()`에 역할과 모드의 조합 분기가 존재합니다.
- B 모드는 현재 A 모드와 동일한 처리 경로를 사용하며 배포 단위와 관측 라벨만 분리됩니다. 모드 이름이 주는 인상보다 실제 차이가 작습니다.
- 모드 조합마다 검증이 필요해 테스트 경로가 늘어납니다.

### 후속 작업

- [x] 역할·토픽 분리 구조 고정
- [x] C·BC 모드의 추론·후단 분리 실구현
- [x] 모드별 부하 실측과 비교
- [ ] B 모드 전용 처리 경로의 필요성 재평가

## 검증 방법

동일 부하 조건에서 모드별 처리량·지연·lag를 비교하고, 전환 시 API 계약과 컨슈머 오프셋이 유지되는지 확인합니다. 관련 문서는 [해결 전략](../architecture/solution-strategy.md)입니다.
