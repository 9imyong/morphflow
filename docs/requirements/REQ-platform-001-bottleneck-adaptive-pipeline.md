# 요구사항: 병목 대응이 가능한 비동기 추론 처리 플랫폼

## 목적과 문제

추론 작업을 동기 방식으로 처리하면 처리 지연이 그대로 API 응답 지연과 타임아웃이 됩니다. 또한 지연이 발생했을 때 원인이 추론 구간인지 그 이후의 저장·전달 구간인지 구분할 수 없으면 잘못된 대응(예: 불필요한 GPU 증설)을 하게 됩니다.

장애를 **예측·대응·복구**할 수 있고, 병목 위치에 따라 구조를 바꿀 수 있는 처리 플랫폼이 필요합니다.

## 이해관계자

| 역할 | 필요한 결과 |
|---|---|
| API 클라이언트 | 처리 지연과 무관하게 즉시 접수 응답을 받고, 이후 상태를 조회할 수 있어야 함 |
| 운영자 | 병목 구간을 지표로 식별하고, 구조 전환과 복구를 절차대로 수행할 수 있어야 함 |

## 요구사항

- REQ-platform-001-01: 클라이언트는 작업을 요청하고 즉시 식별자를 받을 수 있어야 한다.
- REQ-platform-001-02: 클라이언트는 식별자로 처리 상태와 결과를 조회할 수 있어야 한다.
- REQ-platform-001-03: 같은 멱등성 키로 재요청해도 작업이 중복 생성되지 않아야 한다.
- REQ-platform-001-04: 메시지가 중복 전달되어도 결과가 중복 반영되지 않아야 한다.
- REQ-platform-001-05: 처리 실패는 제한된 횟수만 재시도되고, 초과 시 격리되어 파이프라인을 막지 않아야 한다.
- REQ-platform-001-06: 단계별 처리 지연과 적체를 분리해 관측할 수 있어야 한다.
- REQ-platform-001-07: 병목 위치에 따라 추론 또는 후단 처리를 분리 배포할 수 있어야 하며, 전환 시 API 계약과 누적 백로그가 유지되어야 한다.
- REQ-platform-001-08: 두 종류 이상의 아키텍처를 실제 환경에 배포하고 동일 조건에서 비교할 수 있어야 한다.
- REQ-platform-001-09: 장애 시나리오별 탐지 지표와 복구 절차가 문서로 제공되어야 한다.

## 인수 조건

```text
주어진 조건: 처리 용량을 초과하는 요청이 유입되는 상황
실행할 때: 클라이언트가 작업 생성을 요청하면
기대 결과: API는 실패 없이 접수 응답을 반환하고, 미처리 작업은 적체로 관측될 뿐 유실되지 않는다
```

```text
주어진 조건: 워커가 처리 도중 실패한 작업
실행할 때: 재시도 경로로 다시 처리되면
기대 결과: 작업은 최종적으로 성공 상태가 되며 결과는 한 번만 기록된다
```

```text
주어진 조건: 동일한 멱등성 키를 가진 두 번의 요청
실행할 때: 두 번째 요청이 도착하면
기대 결과: 새 작업이 생성되지 않고 최초 작업의 식별자가 반환된다
```

## 범위

### 포함

- 작업 접수, 상태 관리, 비동기 처리 파이프라인
- 멱등성, 재시도, 실패 격리
- 지표·로그·추적 수집과 경보
- 아키텍처 모드 전환과 배포

### 제외

- 실제 추론 모델의 학습과 서빙
- 인증·권한, 멀티테넌시, 과금
- 결과물의 외부 전달과 장기 보관

## 품질과 제약

- 보안: 현재 인증 없음. 신뢰 경계 안에서만 호출된다고 가정합니다.
- 성능: 측정 기준과 결과는 [품질](../architecture/quality.md)에 있습니다.
- 호환성: 아키텍처 모드가 바뀌어도 API 계약과 이벤트 Envelope은 유지합니다.
- 법률 및 규정: 해당 없음. 개인정보를 전제하지 않습니다.
