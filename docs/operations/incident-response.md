# 장애 대응

## 우선순위

1. 사용자와 데이터의 추가 피해를 막습니다.
2. 서비스 상태를 안정화합니다.
3. 관계자에게 사실과 영향을 공유합니다.
4. 원인을 확인하고 안전하게 복구합니다.
5. 재발 방지 조치를 추적합니다.

이 시스템에서는 특히 **사용자 영향 최소화 → 데이터 정합성 보존 → 원인 분석** 순서를 지킵니다. 적체는 사용자 영향이지만 유실은 되돌릴 수 없습니다.

## 역할

| 역할 | 책임 |
|---|---|
| 장애 지휘 | 우선순위와 의사결정 조정 |
| 기술 대응 | 진단과 완화 조치 수행 |
| 소통 담당 | 내부 및 외부 상태 공유 |
| 기록 담당 | 시간대별 사실과 결정 기록 |

현재 운영 인원이 1명이므로 역할은 겸임합니다. 겸임하더라도 **조치 시각 기록은 생략하지 않습니다.**

## 기본 절차

- 장애 등급과 사용자 영향을 판단합니다.
- 관련 런북을 실행하고 모든 조치를 시간과 함께 기록합니다.
- 위험한 변경은 두 사람이 확인하고 되돌리기 준비 후 수행합니다.
- 복구 후 지표와 사용자 흐름으로 정상화를 확인합니다.
- 사후 검토에서 원인보다 시스템 개선에 집중합니다.

## 즉시 실행 체크리스트

1. 영향 범위를 파악합니다: 요청 실패율, 접수 지연, 적체 규모
2. 대시보드와 경보를 확인합니다: Prometheus, Grafana, Kibana
3. 증상에 맞는 런북을 실행합니다.
4. 임시 완화 조치와 영구 해결 조치를 **분리해서** 기록합니다.
5. 복구 확인 후 사후 검토 항목을 생성합니다.
6. 아키텍처 모드 전환이 필요한지 평가하고 판단 근거를 남깁니다.

## 아키텍처 전환 판단

장애 대응 중에는 **모드를 전환하지 않습니다.** 전환은 완화 이후 반복 발생을 확인한 뒤 계획된 변경으로 수행합니다.

| 관측 | 검토할 전환 |
|---|---|
| 처리 시간의 대부분이 추론 구간에 집중되고 진입 적체가 반복 | A → B |
| 추론은 안정적인데 완료까지의 지연과 후단 연동 지연이 증가 | A/B → C |
| 추론 분리 후에도 후단 지표만 악화 | → BC |
| 적체가 단순히 유입 초과 때문 | 전환이 아니라 파티션·워커 확장 |

**배치 처리나 모드 전환만으로 적체를 해소할 수 없는 경우가 많습니다.** 파티션 수가 컨슈머 확장의 상한이므로 확장이 먼저입니다. 근거는 [품질](../architecture/quality.md)의 측정 결과에 있습니다.

## 사후 검토 절차

1. **타임라인 정리**: 탐지 시각, 영향 시작·종료, 완화·복구 시각을 분 단위로 기록
2. **원인 분류**: 직접 원인 / 시스템 원인 / 감지 실패·대응 지연 요인
3. **재발 방지 액션**: 코드·설정·인프라·운영 절차로 분리하고 각각 담당자·기한·검증 기준 부여
4. **검증**: 동일 시나리오 재현(부하 테스트 또는 장애 주입)과 경보 민감도 재점검
5. **문서 반영**: 해당 런북, [위험과 기술 부채](../architecture/risks-technical-debt.md), 필요하면 ADR을 같은 변경에서 갱신

## 에스컬레이션

현재 단일 운영자 환경이므로 외부 에스컬레이션 경로가 없습니다. 운영 환경으로 전환할 때 연락 순서, 응답 제한 시간, 외부 공급자 연락 방법을 정의해야 합니다. 개인 연락처는 이 문서에 기록하지 않습니다.
