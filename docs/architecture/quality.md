# 품질

## 문서 목적

아키텍처에 중요한 품질 목표를 측정 가능한 시나리오로 표현하고 설계 및 검증 방법과 연결합니다.

## 언제 수정하는가

- 성능, 가용성, 보안, 유지보수성 목표가 바뀔 때
- 품질 목표의 측정 방법이나 책임자가 달라질 때
- 운영 결과가 기존 가정을 반박할 때

## 품질 목표 우선순위

1. **관측 가능성** — 병목 구간을 지표로 지목할 수 있어야 합니다. 전환형 아키텍처의 전제입니다.
2. **정합성** — 재처리와 중복 전달에도 결과가 한 번만 반영되어야 합니다.
3. **장애 격리** — 한 단계의 실패가 다른 단계를 멈추지 않아야 합니다.
4. **처리량** — 위 세 가지를 만족하는 범위에서 최대화합니다.

## 품질 시나리오

| ID | 시나리오 | 측정 방법 | 현재 상태 |
|---|---|---|---|
| Q-1 | 부하 중에도 API가 요청을 거절하지 않는다 | k6 50 VU, `http_req_failed` | 달성. A·C 0.00%, B 0.00% |
| Q-2 | API 응답이 처리 지연에 영향받지 않는다 | k6 p95 | 달성. 50 VU에서 18~54ms |
| Q-3 | 처리 실패가 파이프라인을 막지 않는다 | `dlq_messages_total`, 재시도 후 성공률 | 달성. 재시도 후 복구를 회귀 테스트로 검증 |
| Q-4 | 중복 전달이 결과를 중복 반영하지 않는다 | 잠금 경합 회귀 테스트 | 달성 |
| Q-5 | 유입이 처리량을 넘어도 데이터가 유실되지 않는다 | `kafka_consumergroup_lag` | 부분 달성. lag는 누적되지만 유실은 없음 |
| Q-6 | 단계별 병목을 구분해 지목할 수 있다 | 단계별 `*_processing_seconds` | 달성 |

## 측정 결과 (2026-03, k6 60초, 50 VU 기준)

|---|---:|---:|---|
| HTTP req/s | 449.04 | 428.71 | 451.11 |
| p95 (ms) | 28.34 | 53.93 | 32.03 |
| 실패율 | 0.00% | 0.00% | 0.00% |
| 주요 lag | 13,384 (request) | 11,627 (request) | 1 (downstream) |
| 단계 p95 | worker 0.7375s | inference 0.9875s | downstream 0.7375s |

B 모드 수치는 2026-03-12 배치 처리 적용 후 재실측 값입니다. 적용 전 대비 처리량과 실패율은 개선되었고 tail latency는 증가했습니다(`316.73 → 428.71 req/s`, p95 `18.64 → 53.93ms`, 실패율 `0.35% → 0.00%`).

원본 보고서는 [완료 작업 아카이브](../tasks/completed/ARCHIVE-20260310-work-progress-log.md)에서 참조하는 이력 문서에 남아 있습니다.

## 해석과 후속

- 단일 파티션·단일 컨슈머 구간에서는 배치 처리만으로 lag를 해소할 수 없습니다. **파티션 증설과 워커 수평 확장이 선행되어야 합니다.**
- C 모드의 downstream lag가 1 수준으로 유지된 것은 후단 처리 용량이 충분했다는 뜻이며, 후단 병목 상황을 재현한 결과는 아닙니다.
- 아직 측정하지 않은 항목: 10분 이상 soak, downstream replica 1/2/3 비교, 추론·후단 동시 확장 조합.
