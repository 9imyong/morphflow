# RFC-0001: Job 확장 상태 모델과 부분 성공 도입

> 이 문서는 초기 설계 문서에 있었으나 아직 구현되지 않은 구상을 보존한 것입니다. 현재 시스템의 상태 모델은 [데이터 아키텍처](../architecture/data.md)를 기준으로 합니다.

## 요약

현재 Job 상태는 `PENDING`, `PROCESSING`, `SUCCESS`, `FAILED` 네 가지입니다. C·BC 모드에서 추론이 끝나고 후단 처리를 기다리는 Job도 `PROCESSING`으로 남기 때문에, 상태만으로는 어느 단계에 있는지 알 수 없습니다. 단계별 상태와 부분 성공 개념을 도입할지 검토합니다.

## 문제와 동기

- C·BC 모드에서 "추론은 끝났지만 저장이 지연되는" 상황과 "추론 자체가 지연되는" 상황이 같은 상태로 보입니다.
- 후단 처리가 여러 작업(저장·업로드·알림)으로 나뉘면 일부만 성공하는 경우가 생기지만 현재 모델은 전부 성공 또는 전부 실패만 표현합니다.
- 현재는 `job_events`의 `INFERENCE_COMPLETED` 이벤트로만 단계를 구분할 수 있어, 상태 조회 API로는 확인할 수 없습니다.

## 목표와 제외 범위

### 목표

- 단계별 진행 상황을 상태값으로 표현
- 부분 성공을 명시적으로 표현
- 기존 API 소비자의 호환성 유지

### 제외 범위

- 후단 작업의 실제 분리 구현. [RFC-0002](RFC-0002-downstream-task-granularity.md)에서 다룹니다.

## 제안

초기 설계에서 검토했던 확장 상태는 다음과 같습니다.

- `INFERENCE_PROCESSING`
- `INFERENCE_DONE`
- `DOWNSTREAM_PROCESSING`
- `PARTIAL_SUCCESS`
- `RETRYING`

전이 예시:

```text
PENDING → PROCESSING → INFERENCE_DONE → DOWNSTREAM_PROCESSING → SUCCESS
INFERENCE_DONE → DOWNSTREAM_PROCESSING → PARTIAL_SUCCESS
```

## 대안

| 대안 | 장점 | 단점 | 선택 여부 |
|---|---|---|---|
| 현상 유지 (4개 상태 + 이벤트 이력) | 상태 모델이 단순하고 모드 전환에 영향 없음 | 상태 조회만으로 단계 구분 불가 | 현재 채택 |
| 확장 상태값 추가 | 단계가 상태에 드러남 | 모드마다 유효한 상태가 달라져 소비자가 모드를 알아야 함 | 검토 |
| 단계 필드 분리 (`stage` 컬럼 추가) | 상태 모델을 유지하면서 단계 표현 가능 | 컬럼과 API 필드 추가 필요 | 검토 |

## 호환성과 전환

확장 상태값은 기존 소비자가 모르는 값이므로 파괴적 변경입니다. `status`는 유지하고 단계를 별도 필드로 노출하는 방안이 호환성 측면에서 유리합니다.

## 보안과 개인정보

해당 없음. 상태값에 민감정보가 포함되지 않습니다.

## 운영 계획

상태 분포를 지표로 노출하면 단계별 적체를 바로 관측할 수 있습니다. 현재는 `kafka_consumergroup_lag`과 단계별 처리 시간으로 간접 추정합니다.

## 테스트 계획

상태 전이 규칙에 대한 단위 테스트와, 모드별 전이 경로에 대한 통합 테스트가 필요합니다.

## 미결 사항

- 상태값 확장과 단계 필드 분리 중 어느 쪽을 택할지 / 김용준 / 미정
- 부분 성공이 실제로 발생하는 후단 구성이 필요한지 ([RFC-0002](RFC-0002-downstream-task-granularity.md) 선행)

## 검토 결과

미검토. 현재는 4개 상태 모델을 유지합니다.
