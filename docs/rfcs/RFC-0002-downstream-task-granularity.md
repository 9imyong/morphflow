# RFC-0002: 후단 처리를 작업 단위로 분리

> 이 문서는 초기 설계 문서에 있었으나 아직 구현되지 않은 구상을 보존한 것입니다. 현재 후단 처리는 단일 더미 작업이며 기준은 [실행 흐름](../architecture/runtime.md)입니다.

## 요약

현재 후단 처리는 하나의 덩어리이며 지연만 재현하는 더미 구현입니다. 실제 후단 처리는 저장·업로드·외부 호출·알림처럼 서로 다른 실패 특성을 가진 작업의 묶음입니다. 이를 작업 단위로 분리해 개별 재시도와 상태 추적을 할지 검토합니다.

## 문제와 동기

- 후단 작업 중 하나만 실패해도 전체가 실패로 기록됩니다.
- 재시도 시 이미 성공한 작업까지 다시 수행합니다.
- 작업별 지연 특성이 섞여 어느 연동이 느린지 구분할 수 없습니다.

## 목표와 제외 범위

### 목표

- 후단 작업을 유형별로 분리해 개별 재시도
- 작업 단위 멱등성 보장
- 작업 유형별 지연·실패 지표 분리

### 제외 범위

- 부분 성공 상태 표현. [RFC-0001](RFC-0001-extended-job-status-model.md)에서 다룹니다.

## 제안

초기 설계에서 검토했던 구조는 다음과 같습니다.

`downstream_tasks` 테이블:

| 컬럼 | 의미 |
|---|---|
| `id` | 기본 키 |
| `job_id` | 연관 Job |
| `task_type` | `upload`, `notify`, `external_api` 등 |
| `status` | 작업 상태 |
| `retry_count` | 재시도 횟수 |
| `last_error` | 최근 오류 |

멱등성 키는 `idem:downstream:{job_id}:{task_type}` 형태로 작업 단위까지 구분하고, `job_id + task_type` 유니크 제약으로 중복 실행을 막습니다.

## 대안

| 대안 | 장점 | 단점 | 선택 여부 |
|---|---|---|---|
| 현상 유지 (단일 후단 작업) | 단순. 현재 검증 목적에 충분 | 부분 실패 표현 불가 | 현재 채택 |
| 작업 단위 테이블 분리 | 개별 재시도와 추적 가능 | 테이블·상태·멱등성 키가 늘어남 | 검토 |
| 작업 유형별 토픽 분리 | 유형별 독립 확장 가능 | 토픽과 컨슈머 그룹 관리 비용 증가 | 검토 |

## 호환성과 전환

`jobs` 테이블과 API 계약은 바뀌지 않습니다. 새 테이블 추가이므로 마이그레이션은 하위 호환입니다.

## 보안과 개인정보

외부 연동이 실제로 생기면 자격증명 관리와 전송 데이터 분류가 선행되어야 합니다.

## 운영 계획

작업 유형별 지연과 실패를 별도 지표로 노출하고, 유형별 DLQ 분류를 적용합니다.

## 테스트 계획

작업 단위 멱등성(같은 `job_id + task_type` 중복 실행 방지)과 부분 실패 후 재시도 시 성공한 작업을 건너뛰는지 검증합니다.

## 미결 사항

- 실제 외부 연동 대상이 정해져야 작업 유형을 확정할 수 있음 / 김용준 / 미정

## 검토 결과

미검토. 현재는 단일 후단 작업을 유지합니다.
